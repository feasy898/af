   **核验点**：T3 若动了 `credential.rs`，`verify_limits()` 的**三个调用点一个都不能丢**。丢了不会在单跑时暴露，只在满载 `-j 6` 偶挂 —— 这正是当初的漏网形态。**验收必须用 `-j 6` 跑两轮**。

   `crates/af-credential/RESULT.md:53`：「**预算不能住在凭证里**。衰减单调性：预算从 10 降 5 无法表达为"改事实"，只能叠加更紧的 per-call cap check；且 `spend_cents` 是验证方声明的事实，凭证管不住累计消耗。结论：累计预算真相源放 af-meter 账本，凭证只携带 per-call 上限（或预算主体绑定），网关按账本余量注入 spend。」

### (a) 合流前必须核验的已验证语义（含坑）

2. **⚠ 坑 1（必须删除的"字面 FNV 契约"测试）**

3. **⚠ 坑 2（长度断言在下游）**

5. **⚠ 坑 3（ed25519：`seal()` 的存在性被破坏，这是本次最硬的 API 断点）**

   - `decision.rs:86` `pub const SIGNATURE_ALGORITHM_PLACEHOLDER: &str = "ed25519-placeholder";`

### (a) 合流前必须核验的已验证语义（含坑）

1. **待改的时钟源（逐行确认）**

   - 唯一的墙钟读点：`lib.rs:445` `let now = now_ms();`（execute 内）与 `lib.rs:472`（record_receipt 内）；声明时 `:305` `let deadline = now + self.withdraw_window.as_millis() as i64;`

2. **⚠ 核心张力（本分支的阻断级设计问题，必须先裁决再 review 代码）**
   **撤回窗口的 deadline 是持久化到 SQLite 的**：
   - `lib.rs:237` 建表：`withdraw_deadline_ms INTEGER NOT NULL`
   - `lib.rs:312` INSERT 时写入
   - `lib.rs:446` execute 时 `if now < deadline { return Err(WindowStillOpen { … }) }` 读出比较
   - `lib.rs:372` withdraw 的 SQL 谓词 `AND withdraw_deadline_ms > ?4`

   而**Rust 的单调钟（`std::time::Instant`）是进程本地的**，跨进程重启后与墙钟无任何可比关系。

   → **T7 必须在下面三条路径里选一条，并在 RESULT.md 里写下理由**：
   - **(i) 双时钟分工**：进程内测量（超时节流等）用 `Instant`；**撤回窗口的持久化 deadline 仍用墙钟**。这是唯一不破坏 `t1_crash_recovery_same_key_same_payload_replays_stored_result` 的路径。
   - **(ii) 持久化锚点**：落库时同时存 `wall_ms` 与 `boot_id + mono_ms`，比较时先判 `boot_id` 是否同当前进程，不同则回落到墙钟。复杂且要处理 NTP 跳变。
   - **(iii) 纯 `Instant`**：**直接违反 `crates/af-effect-gateway/RESULT.md:15` 的 t1 用例语义** —— declare → drop → 重开库 → resume → 重放，窗口状态在重启后无法判断。**不可选。**

   **review 第一条：确认 T7 选了 (i) 或 (ii)，且 (iii) 的方案要打回。**

3. **✅ 好消息：`t1` 用例不依赖窗口时间的绝对值**
   `crates/af-effect-gateway/RESULT.md:15` 的崩溃恢复场景是：declare → execute（外呼 1 次）→ drop → 重开库 → resume（纪元 0→1）→ 同键同载荷重放 → 返回 `txn T-1`，计数器仍为 1。
