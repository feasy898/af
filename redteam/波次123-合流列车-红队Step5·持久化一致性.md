## 0. 先交代：作者的完成声明与代码的差距在哪里

六个 crate 的 `RESULT.md` / `RESULT-UPDATE*.md` 我逐条对过代码。**测试计数全部属实**（见 §3 第 1 条），每条声明背后的测试也都真实存在且全绿。差距不在"声明了没做"，而在三类：

## 2. 详细发现

### F1（high）`DurableGate` 重启后打不开：wip 的位型比较把合法状态判成损坏

**位置**：`crates/af-release-gate/src/store.rs:663-672`（`load_runtime` 的重算与比较）、`crates/af-release-gate/src/gate.rs:654-657`（`restore_runtime` 的同一比较）；写入侧 `crates/af-release-gate/src/store.rs:306`（`f64_to_sql(snap.wip)`）；累加侧 `crates/af-release-gate/src/gate.rs:522`（`self.wip += item.review_minutes`）、`:553`（`self.wip -= q.ticket.weight`）、`:879`（rollback 同减）。

**问题**：闸门的 `wip` 是随准入/完成**增量累加**出来的 `f64`；落库时存的是这个累加值。重启时 `load_runtime` 按在制队列顺序**重新从左到右加一遍**，然后：

```rust
// crates/af-release-gate/src/store.rs:663-672
let sum = items.iter().fold(0.0, |acc, item| acc + item.weight);
if sum.to_bits() != wip.to_bits() {
    return Err(PersistError::Corrupt { detail: format!("wip bits {:x} != item sum {:x}", ...) });
}
```

浮点加法不满足结合律，从队列中间 `remove` 一件之后，累加值与重算值在最后几位上会分叉。一旦分叉，`DurableGate::open` 永久返回 `Corrupt`——**没有任何恢复路径**（连手工修都要改库）。写入时没有任何告警，错误只在重启那一刻出现。

**为什么 43 个全绿测试没抓到**：重启 proptest 的权重生成器是 `u16`（`crates/af-release-gate/tests/properties.rs:89`、`:116`），调用处是 `f64::from(weight)`（`:348`、`:690`）。`u16` 转 `f64` 恒可精确表示，加减也精确，累加值与重算值永远逐位相同。整数分钟安全，分数分钟（例如把 45 分钟审阅折成 0.75）立刻触发。

**证据**（独立复现 crate `/tmp/rt`，path 依赖 af-release-gate；命令 `cd /tmp/rt && cargo run --offline`）：

```rust
// 复现程序主体
let weights = [5.7f64, 0.2, 0.3, 0.01, 0.01, 0.3];
for (i, w) in weights.iter().enumerate() {
    dg.try_admit(&Item { id: i as u64 + 1, config: "c".into(), review_minutes: *w }, 0).unwrap();
}
dg.complete(1, 1, 0).unwrap();   // 从队列中间完成两件
dg.complete(5, 1, 0).unwrap();
drop(dg);
match DurableGate::open(&path, &cfg(), None) { ... }
```

```
A running wip = 0.8099999999999994  bits=3fe9eb851eb851e6
A fresh   sum  = 0.81  bits=3fe9eb851eb851ec
A first open outcome = Created
A durable wip = 0.8099999999999994
A REOPEN FAILED: persisted state is corrupt: wip bits 3fe9eb851eb851e6 != item sum 3fe9eb851eb851ec
```

随机序列的命中率（同一算术的 Python 等价模拟，20 万例）：

```
$ python3 /tmp/wipcheck.py
mismatches: 119190 of 200000
```

### F2（medium）六个 store 的首启竞态全部落在 `PRAGMA journal_mode=WAL` 上，`busy_timeout` 救不了

**位置**：`crates/af-meter/src/ledger/mod.rs:366`、`crates/af-sampling/src/persist.rs:495`、`crates/af-release-gate/src/store.rs:459`、`crates/af-stop/src/ledger.rs:357`、`crates/af-credential/src/root.rs:671`、`crates/af-trace/src/store.rs:112`——六处都是"先 `busy_timeout`、再 `journal_mode=WAL`、最后才进事务"。

**问题**：把一个 0 字节的新文件从 `delete` 转到 `wal` 需要排他锁，而这条转换路径**不调用 busy handler**——`busy_timeout(5000)` 设了也白设。于是两个进程/线程同时首启同一个空路径，后来者直接拿到 `sqlite: database is locked`。af-meter 的 RESULT-UPDATE ⑤ 把这个场景列为未测，并给出假设"初始化事务是 `BEGIN IMMEDIATE`，后到的一方会看到已经写好的 `user_version`"——**实测失败发生在任何事务之前**，那个假设不成立。崩溃安全性本身没被破坏（返回错误、不写半截库），但并发首启（双 worker 同时拉起、systemd 重启竞速）会直接 crash-loop。

**证据**（6 线程 + `Barrier` 同时 `Ledger::open` 同一个全新路径，`/tmp/rt`，`cargo run --offline`，连跑三次）：

```
K af-meter: threads=6 created=1 already=0 errors=5 reopen_after=Ok("false")
K   err: thread 2: sqlite: database is locked
K   err: thread 3: sqlite: database is locked
K af-sampling: threads=6 created=1 already=4 errors=1 reopen_after=Ok("AlreadyDeclared")
K   err: thread 1: sqlite: database is locked
K af-release-gate: threads=6 created=1 already=5 errors=0 reopen_after=Ok("AlreadyDeclared")
```

逐步插桩，确认是哪一步丢锁（6 线程，6 个 trial）：

```
trial 5: ok=4 failing_step=[("journal_mode", "open;busy;fk;sync; ERR database is locked"), ("journal_mode", "open;busy;fk;sync; ERR database is locked")]
```

前 4 个 trial 全 ok，第 5 个 trial 2/6 失败——竞态窗口窄但真实存在，重跑即可复现。

### F3（medium）`af-release-gate` 首建库的 TOCTOU：DEFERRED 事务 + 裸 `CREATE TABLE`

**位置**：`crates/af-release-gate/src/store.rs:173`（`table_exists(&conn, "gate_meta")` 判断）、`:370`（`any_user_table` 判断）、`:465-477`（`create_schema`：`let tx = conn.transaction()?;` 是 **DEFERRED**，`:471`；`SCHEMA_SQL` 用的是裸 `CREATE TABLE`，没有 `IF NOT EXISTS`，`:36`、`:53`、`:61`）。

**问题**：`table_exists` 检查与 `create_schema` 之间没有原子性。两个首启者都通过 `gate_meta` 不存在、都通过 `any_user_table` 为假，然后都去建表；后到者的 `CREATE TABLE gate_meta` 撞已存在的表。af-meter（`crates/af-meter/src/ledger/mod.rs:271`）和 af-stop（`crates/af-stop/src/ledger.rs:382`）的首建用的是 `TransactionBehavior::Immediate`，那把锁才让"后到者看到已写完的 `user_version`"成立；af-release-gate 是六个里唯一用 DEFERRED 的。

**证据**（同 F2 的竞态程序，第三次运行）：

```
K af-release-gate: threads=6 created=1 already=3 errors=2 reopen_after=Ok("AlreadyDeclared")
K   err: thread 1: sqlite: database is locked
K   err: thread 3: sqlite: table gate_meta already exists
```

（`reopen_after=Ok("AlreadyDeclared")` 说明库最终是一致的，错误路径本身 fail-closed；问题是错误形态不可读、且与 F2 叠加后并发首启几乎必失败。）

### F4（medium）`af-trace` 的 `Trace::open` 会把外来的 `trace.db` 收编成自己的首启

**位置**：`crates/af-trace/src/store.rs:121-155`（`init_or_check`）：`tx.execute_batch(SCHEMA)` 用的是 `CREATE TABLE IF NOT EXISTS`（`:20`、`:26`），然后 `SELECT ... FROM declaration WHERE id = 1`，取不到行就 `INSERT` 并返回 `OpenOutcome::Created`。全程没有"这个库必须是空的"这一步。

**问题**：`TraceConfig.dir` 指向的目录里如果已经有一个别的东西写的 `trace.db`（同名不同主），`Trace::open` 会往里加两张表、回报 `Created`，之后两个组件共用一个 SQLite 文件。其他五个 crate 都有这道关：af-meter `exact_tables`（`ledger/mod.rs:425-438`）、af-sampling `check_tables`（`persist.rs:583-591`）、af-release-gate `any_user_table`（`store.rs:370`）、af-stop `(0, _, true)` 分支（`ledger.rs:214-218`）、af-credential `ensure_tables` + `(true,true)` 文件对（`root.rs:250-268`）。af-trace 只防了反方向（有 jsonl 没 db，`trace.rs:525-535` 的 `reject_orphan_logs`），没防"有 db 但 db 不是我的"。

**证据**（`/tmp/rt`，`cargo run --offline`）：

### F5（medium）`Reading::recovers_at`：同一个字段两套时间单位，类型完全相同

**位置**：`crates/af-meter/src/lib.rs:39-40`（`pub type Time = u64;`，注释"自任选纪元起的整数秒"）、`crates/af-meter/src/lib.rs:52-59`（`Reading { available: Count, recovers_at: Option<Time> }`）；账本路径 `crates/af-meter/src/ledger/consume.rs:84`（`let recovers_at = ms_to_time(end_ms)?;`）与 `:351`（`recovers_at: Some(ms_to_time(end_ms)?)`），`ms_to_time` 是 `u64::try_from(ms)`（`ledger/mod.rs:348-350`）——**Unix 毫秒**。作者在 `crates/af-meter/src/ledger/mod.rs:8-9` 和 af-meter RESULT-UPDATE ④1 明确写了这个坑。

**问题**：`Time` 是同一个 `u64` 别名，`Reading` 是同一个 struct。任何把账本读数交给按 `Meter` 语义写的代码（"再等 N 秒"）的调用方，都会差 1000 倍，且编译器一声不响。目前 af 仓库内没有跨路径调用者（我 grep 过：`recovers_at` 在 af-meter 之外零命中），所以是**已披露的潜伏雷**，不是正在炸的 bug；但把它列为"已知"而不做类型隔离，等于把正确性责任推给每一个未来的调用方。

**证据**（`/tmp/rt`，同一次运行里两条路径都打出来）：

```
D ledger recovers_at = Some(1782079200000) (unix ms)
D window end_ms      = 1782079200000 (unix ms)
D meter  recovers_at = Some(86400) (integer seconds)
```

### F6（medium）`af-credential`：`root.key` 与 `credential.db` 之间崩溃 = 永久起不来

**位置**：`crates/af-credential/src/root.rs:476-477`（注释"首启还没提交。写到一半的文件删掉，下一次 open 仍能走 Created。"）、`:477`（`write_key_file(...).inspect_err(|_| discard_new_store(dir))?`）、`:505-511`（DB 建失败才 `discard_new_store`）、`:250-268`（`match (key_exists, db_exists)`：`(true, false)` → `RootError::Incomplete`）。

**问题**：`create_store` 的顺序是**先写 `root.key`，再建 `credential.db`**。`discard_new_store`（删 root.key + 删 db 三件套）只在**进程内出错**时跑。真实崩溃（kill -9 / 断电 / OOM）发生在两者之间时，留下 `root.key` 在、`credential.db` 不在，此后每次 `open` 都走 `_ => Err(Incomplete)` 分支——注释承诺的"下一次 open 仍能走 Created"不成立，目录**永久**起不来，只能人工删文件。作者在 RESULT-UPDATE ⑤ 记了"当前私钥丢了且没有匹配的 journal 时，目录起不来"，但没记这一条更窄、更容易踩的窗口。

**证据**（`/tmp/rt`，`cargo run --offline`）：先正常 `open` 建好 store，再删掉 `credential.db`（模拟崩溃窗口），然后连续两次 `open`：

```
H open #0 FAILED: root store is incomplete: root.key and credential.db must both exist
H open #1 FAILED: root store is incomplete: root.key and credential.db must both exist
```

### F7（low）"对不上就失败，不改库"——改的是文件头和权限，不是行

**位置**：见 F2 列出的六处 `journal_mode=WAL`；af-credential 另有 `crates/af-credential/src/root.rs:676`（`set_mode_0600(path)?` 作用在 `credential.db` 上）与 `:677-683`（顺手把已存在的 `-wal` / `-shm` 也 chmod 0600）。文档侧对应 `crates/af-credential/src/root.rs:9`（"文件损坏、权限不是 0600、schema 或声明对不上，都直接失败，不生成新密钥"）与 `crates/af-meter/src/ledger/mod.rs:266`（"其余情况返回错误，不改库里的行"）。

**问题**：六个 store 都在做任何版本/声明校验**之前**执行 pragma。拒绝一个外来库时，行确实一个不改（已实测），但那个文件的 `journal_mode` 被从 `delete` 翻成 `wal`，af-credential 还把它的权限从 0644 改成 0600。文档的措辞（af-meter 精确到"不改库里的**行**"）算是诚实的；af-credential 的"直接失败，不生成新密钥"容易被读成"什么都不动"。

**证据**（`/tmp/rt`）：

G foreign journal_mode AFTER af-meter open = wal, rows in mine = 0

### F8（low）`af-credential` 的 `credential.db` 没有 `PRAGMA user_version` 门

**位置**：`crates/af-credential/src/root.rs:721-735`（`ensure_tables`：只数三张表在不在）、`:762-768`（`check_decl`：只比 `schema_meta.schema_version` 列）；对比 af-meter `crates/af-meter/src/ledger/mod.rs:305-310`（`user_version != SCHEMA_VERSION` → `SchemaMismatch`）与 af-stop `crates/af-stop/src/ledger.rs:219-236`（同一套）。

### F9（low）`af-sampling` 写事务是 DEFERRED，`busy_timeout` 对第二写者失效

**位置**：`crates/af-sampling/src/persist.rs:303`（`observe`：`let tx = self.conn.transaction()?;`）、`:400`（`persist_promotion`：同一写法）。文档侧对应 `crates/af-sampling/src/persist.rs:10-11`（"开库配方与 af-station 相同：WAL、`busy_timeout` 5000ms、`synchronous=NORMAL`、`foreign_keys=ON`"）。

**问题**：配方与 af-station 相同，**事务行为不同**。af-stop（`crates/af-stop/src/ledger.rs:319-321`）、af-meter（`ledger/consume.rs:90-92`）、af-credential（`root.rs:443`）的写事务都用 `TransactionBehavior::Immediate`；af-sampling 两条写路径都是默认 DEFERRED。DEFERRED 事务在 WAL 下先拿读快照、写时再升级；这期间若有别的连接提交过，升级会直接返回 `SQLITE_BUSY`（busy handler 不兜这种快照失效），`busy_timeout=5000` 形同虚设。crate 文档说"一个实例持有一条 SQLite 连接"，所以今天只影响多实例部署——但配方里留着 5000ms 的 busy_timeout 会让人以为多写者是被接住的。

**证据**（`/tmp/rt`，两条连接、A 先开 DEFERRED 读事务、B 提交、A 再写）：

```
E deferred write FAILED: database is locked
```

（两条连接的 `busy_timeout` 都设了 5000ms，仍然立即失败。）

### F10（low）窗口"两端都是当地 00:00"的文档承诺，对 8 个时区不成立

### F11（low）`NightWindow` 表达不出"全天窗口"

**位置**：`crates/af-release-gate/src/gate.rs:63-72`（`contains`：`start == end` 直接 `false`）、`:319-328`（`ReleaseGate::new` 校验 `m >= 1440` → `ConfigError::BadNightMinute`）。

**问题**：`MinuteOfDay` 的域是 `0..=1439`，而窗口是半开区间 `[start, end)`。想配"全天按 ratio 限流"只有两种写法，两种都不成：`start=0, end=1440` 被 `BadNightMinute(1440)` 拒掉；`start=0, end=0` 能过校验，但 `contains` 的 `start == end → false` 让它**静默变成空窗口**——不报错、不限流，监控上看不出来。想要覆盖 23:59 这一分钟的非跨午夜窗口同样做不到（`end` 最大 1439）。

**证据**（`/tmp/rt`）：

```

C night [0,0) accepted; in_night_window(0)=false in_night_window(1439)=false
```

## 4. 给处置方的优先级建议（不评优劣，只排先后）

1. **F1 先修**：唯一一条"合法操作序列 → 组件永久起不来"的，且现有测试生成器结构性看不到它。最小修法是把 `load_runtime` / `restore_runtime` 的位型比较换成容差比较，或落库时存重算值而不是累加值。
2. **F2 + F3 一起修**：把 `journal_mode=WAL` 挪进首建事务之后（或对"文件已存在"与"全新文件"分两条路），并给 af-release-gate 的 `create_schema` 换成 `TransactionBehavior::Immediate`。修完 F2/F3 后，af-meter RESULT-UPDATE ⑤ 里那条"未压测"就可以正式补上测试。
3. **F4 + F13 一起修**：给 af-trace 补"库必须是空的"这道关；借 af-meter 的 `extra_table_fails_closed` 给另外四个 crate 各补一条。
4. F5 需要调用方出现之前做类型隔离（例如给账本路径一个独立的毫秒 newtype），否则只会一直以"已知遗留"的形式存在。
5. F6/F8/F11 是窄窗口或配置表达力问题，可排期。
