## H1（high）af-release-gate `DurableGate`：分数权重下合法状态重启即 Corrupt，账本永久打不开

**会出什么问题**：`review_minutes` 的公开类型是 `f64`（`Item.review_minutes`、`ReleaseGate::admit(review_minutes: f64)`），但账本重开时用**逐位比较**校验 `wip == Σitems`。运行期 `wip` 是增量维护的（admit `+=`、complete `-=`），f64 减法不可结合，完成一件之后增量值与队列重求和值可以差 1 ULP。此时 `load_runtime` 判 Corrupt，`open` 失败——而且**没有任何修复路径**，这个库文件从此每次 open 都失败。运营上只剩两条路：闸门永久不可用，或删库重建——删库即 WIP 清零，正是 W2C「重启后 CONWIP 不超发」声称要防的事故。

**证据（已复现，公开 API）**：

```
$ cargo run   # /tmp/af-redteam-check，DurableGate::open_with_clock + try_admit(0.1) + try_admit(0.2) + complete(0.1) 后 drop 重开
[1] wip after admits = 0.30000000000000004
[1] wip after complete(0.1) = 0.20000000000000004
[1] in_process = [InProcessItem { id: 2, config: "v1", weight: 0.2, admitted_at: 0 }]
[1] reopen FAILED: persisted state is corrupt: wip bits 3fc999999999999b != item sum 3fc999999999999a
```

- 检查点：`crates/af-release-gate/src/store.rs:663-672`（`sum.to_bits() != wip.to_bits()` → `Corrupt`）；同一检查在 `crates/af-release-gate/src/gate.rs:654-657`（`restore_runtime`）。
- 增量来源：`crates/af-release-gate/src/gate.rs:522`（`self.wip += item.review_minutes`）、`gate.rs:553`（`self.wip -= q.ticket.weight`）。
- 数值根源（IEEE754，Python 同规）：`0x1.999999999999ap-3`（(0.1+0.2)-0.1）≠ `0x1.999999999999bp-3`（0.0+0.2）。

**声明差距**：W3C `RESULT-UPDATE.md` ①「`cargo test -p af-release-gate` 43 全绿」与「重启后不超发」只覆盖整数权重——`tests/properties.rs:88-91` 的 `Op::Admit { weight: u16 }` 与 `properties.rs:152`（`1u16..=50`）保证 proptest 全部生成整数值权重，f64 加减在整数域恒精确，因此 `conwip_does_not_over_release_after_restart` 结构上不可能踩到该路径。`tests/persist.rs` 的 17 个用例同样只用整数/二进分数权重。声明里的「在制与游标原样装回」对公开 API 允许的输入（任意有限正 f64）不成立。

**附带（同组件、另一条触发路径）**：`write_snapshot`（`store.rs:321-322`）先 `DELETE FROM wip_item` 再重插，无纪元、无版本守卫。两个进程同时 `DurableGate::open` 同一文件时后写者整表覆盖前者在制（无任何告警），WIP 被静默低估→超发。文档只说「一个实例持有一条连接」（`store.rs:132-133`），未声明互斥；af-effect-gateway 好歹有纪元 fencing，这里什么都没有。

## H2（high）af-effect-gateway：fencing 只在入口查一次，外呼在闸门保护之外——同纪元两连接并发 `execute` 外呼两次（已复现）；崩溃窗口与模块文档承诺相反

**会出什么问题**：`execute` 的顺序是 `fence()`（一次性读纪元）→ 读状态 → 调 `effect` 闭包 → `store_receipt`。外呼与回执落库之间既无事务也无纪元复核。两个后果：

1. **并发双发（已复现）**：两条连接对同一库各 `attach()`（纪元相同，谁也没 `resume`），并发 `execute` 同一意图——两者都过 fence、都读到 `declared`、都执行外呼。RESULT ④.5 设想的「生产多进程需每 session 一条连接」恰好就是这个形态。
2. **fencing TOCTOU**：`store_receipt` 的 UPDATE（`lib.rs:666-678`）只守卫 `state='declared'`，不校验纪元。P1 过完 fence 后开始外呼期间 P2 `resume()` 接管并执行同一意图，P1 的外呼照发、回执照落——「旧纪元请求一律拒绝」只在入口成立，不在提交点成立。

**证据（已复现）**：

```
$ cargo run   # /tmp/af-redteam-check：同文件两次 open_with_clock，两个 attach() session，Barrier 对齐后并发 execute
[4] epochs: s1=0 s2=0
[4] executor slow=true ok=true replay=Some(false)
[4] executor slow=false ok=true replay=Some(false)
[4] external effect invoked 2 times
[4] final intent state = Executed
```

外呼计数 2、两个执行者都拿到 `RanFresh`（非重放）——「外呼恰好一次」的核心承诺被打破。

**声明差距**：模块文档 `crates/af-effect-gateway/src/lib.rs:4-5`：「进程可能在 declare 之后、**外部调用前后任意点崩溃**；恢复后重放**不能导致重复发送**」。按代码顺序（`lib.rs:625` 外呼 → `lib.rs:627` 落回执），在外呼成功与回执落库之间崩溃后重放，必然第二次外呼——这条窗口文档RESULT ④.5 有半句承认（「网关防的是已成功的重复发送」），但 lib.rs 的头两条承诺仍是强的，且 W3B RESULT-UPDATE 只说「幂等、fencing、撤回窗口没有回退」，未提单连接假设在多进程部署下的失效条件。

## M1（medium）fuzz 工作区 `Cargo.lock` 从首个提交起就带未解决合并冲突标记，main 上无法构建，「两 target 各 2000 次无 panic」不可从提交树复现

**会出什么问题**：`cargo` 在 `fuzz/` 下任何命令都因锁文件 TOML 解析失败而终止；fuzz 冒烟声明对应的工件在 main 上不存在可构建版本。合流列车把冲突文本直接提交进了 main。

**证据**：

```
$ cd af/fuzz && cargo check --offline
error: failed to parse lock file at: .../af/fuzz/Cargo.lock
    TOML parse error at line 6, column 9
$ git show <c>:fuzz/Cargo.lock | grep -c '<<<<<<<'
607a4b7(建 fuzz 工作区): 9   814bdb6: 23   73bc975: 47   HEAD: 47
```

- 标记数随每次 fuzz 提交递增（9→23→47），说明每次「合流」都在冲突文本上继续叠加，从未发现——因为主工作区测试与 CI 门都不编 fuzz（空 `[workspace]` 隔离）。
- 与 c22711c「写入 RESULT-UPDATE：两 target 各 2000 次无 panic」的声明冲突：该 RESULT-UPDATE 的父提交（73bc975）已含 47 段冲突标记，提交树内无法跑出该结论。

## M2（medium）af-station 并发冷启动竞争：多 worker 同时首开同库，~35% 轮次出现裸 sqlite 错误而非 `Created/AlreadyDeclared`

**会出什么问题**：RESULT.md ④.1 的部署模型是「多 worker = 各自 open 同一个 db 文件，正确性不依赖进程内锁」。N 个 worker 冷启动（首部署正是所有 worker 同时拉起的时刻）竞争建表：看到空库的多个连接都走 `create_schema`，输家拿到 `table station_decl already exists`；WAL journal_mode 切换的排他锁竞争则直接报 `database is locked`（busy_timeout 对 journal_mode 变更不总生效）。worker 启动即崩，且错误不是声明协议的一部分。

**证据（已复现）**：8 线程 Barrier 对齐后并发 `Station::open` 同一新文件，20 轮中 7 轮（0/2/5/8/12/16/17）出现失败；round 16 两种形态同时出现：

```
[3] round=16 results=["ERR: sqlite: database is locked", "Created", "AlreadyDeclared", ..., "ERR: sqlite: table station_decl already exists"]
```

- 代码路径：`crates/af-station/src/schema.rs:67-71`（`user_objects` 为空 → `create_schema`，两步之间无互斥）；`schema.rs:62-64`（busy_timeout/WAL 设置顺序）。
- 声明差距：W2G RESULT-UPDATE ①「开库改为声明……`AlreadyDeclared` 为重入且库内声明与代码一致」未提并发首开的失败形态；既有并发测试（`tests/concurrency.rs`）都在库**已建好**之后才开连接，覆盖不到冷启动窗口。

## M3（medium）W3E 编排壳绕过引擎的 `approve_decision`：审批门是裸 signal 字符串，无决策工件、无验签；引擎侧 `approve_decision` 也不绑定工单身份

**会出什么问题**：审批链两端都是空的。编排端：`workflow.py` 的审批门只等 `approved_by` 字符串置位（任何人发 `approve` signal 即过），全程没有调用引擎的 `approve_decision`——而 af-engine 的 README/W3A RESULT-UPDATE 明文把 `approve_decision` 列为「必经引擎」，且反馈①说「编排层要自己先调 approve_decision，再调 release」。引擎端：即便调了，`approve_decision` 验的是调用方自带 `payload` 字符串与工件的哈希一致（`crates/af-engine/src/lib.rs:188-194`），契约样例的 payload 是自由串 `"wo-1:release-request:g-3"`（`tests/contract/approve_decision_ok.request.json`），不是 `WorkOrder::decision_payload` 的域分隔格式——W3D 声明「订单决策要带上身份，走 `WorkOrder::seal_decision`」，引擎边界不强制。

**证据**：
- `orchestration/workflow.py:149-151`（`wait_condition(lambda: bool(s.approved_by))`）、`workflow.py:187-190`（signal 直接写 `f"signal:{approver}"`）；`grep approve_decision orchestration/` 无命中。
- W3E 提交 f6cb367 声明「判定全走引擎 ✅」与「审批门 signal……归 Python」并存——审批是否发生这一判定并不在引擎。
- 引擎契约样例 payload 见上；四层校验的锚定对象由调用方自选。

**顺带（同属快照信任缝）**：`decode_work_order` 不校验 state 与履历的一致性。已验证：`{"state":"Closed","history":[],...}` 可成功解码（`/tmp` 复现输出 `[5] decode OK: state=Closed history_len=0`）——状态机上不可能的组合（Closed 必有 4 条履历）原样入库。下游 af-effect-gateway 的订单态门控按「递交的那张工单」判定（W3B ⑤ 已声明信任调用方），编排层 JSON 快照的一个 bug 就能把 `InProgress` 伪快照送过执行闸。

## L1（low）W3C 证据声明「没有 sleep」与代码不符

`crates/af-release-gate/tests/gate_unit.rs:295` 存在真实 `thread::sleep(Duration::from_millis(150))`（`blocking_admit_wakes_on_completion`，等待生产者线程进入阻塞）。W3C RESULT-UPDATE ③证据节原文：「时刻由测试传入 `MinuteOfDay`，**没有 sleep**」。该 sleep 是同步用途而非闸门时间，且原 RESULT.md ③ 已如实记录过它，但 W3C 的全称否定声明与仓库代码矛盾。

## L2（low）`engine_calls.log` 观测字段是死路：`state_after`/`missing` 永远为 null

`orchestration/workflow.py:58-63` 写日志时取 `resp.get("state")` 与 `(resp.get("error") or {}).get("detail",...)`，而引擎成功响应是 `{"ok":true,"order":{...,"state":...}}`（状态在 `order.state`），失败响应是 `{"kind":"Gate","gate":{...}}`（无 `detail` 键）。实测 `data/engine_calls.log` 首页 5 条全部 `"state_after": null, "missing": null`——包括成功调用。W3E 声称该轨迹记录「哪个版本引擎判了什么」，拒绝原因从未被记下。另 `tag`/`transition` 字段是已废除形参的残留，恒 null。

## L3（low）夜间信用在 WipCap 处空烧 + `admitted` 计数虚增已被测试钉死为「预期」，但与「长期放行率精确 = ratio」的声明自相矛盾；`admit_blocking` 在夜间窗口内每轮重试烧一份信用

复现：upper=1.0、ratio=1.0，准入 0.6 后再请求 0.6 → `WipCap`，`night_stats=(requests=2, admitted=2)` 而 `in_process=1`——`admitted` 计入了一次从未发生的准入。该行为被 `tests/persist.rs:537` 显式断言为预期（WipCap 拒后 `(1,1)`），RESULT.md ④.4 也承认「信用已扣」。声明差距在：RESULT.md ②「窗口进出时重置，长期放行率精确 = ratio」与其自家 day_sim 实测 0.317 vs 0.3（RESULT.md ③）矛盾；且 `SharedGate::admit_blocking`（`gate.rs:726-747`）在夜间窗口内于 WipCap 上原地重试，每次重试都 `requests+=1`、累计并烧掉整份信用——RESULT ④.3 只告诫「调用方不要原地重试」，闸门自己在阻塞路径上就这么做。

## L4（low）af-effect-gateway `Gateway` 与 `Cell`：`observed_mono` 用 `Cell<i64>`，`Gateway` 非 `Sync`

`crates/af-effect-gateway/src/lib.rs:283`（`observed_mono: Cell<i64>`）使 `&Gateway` 无法跨线程共享（`Connection` 本就非 Sync，二者叠加）。这是「单线程语义」的编译期体现，与 H2 是同一假设的两面；若有人按 RESULT ④.5 的建议上 `Mutex<Gateway>` 尚可，直接 `Arc<Gateway>` 会编译失败——失败是好事，问题是文档没有写明这个约束，`open()` 的文档也未声明单线程独占。

## L5（low）af-station 租约用可回拨墙钟（`SystemClock` 读 `SystemTime`），与网关 T7 的单调钟标准不一致

`crates/af-station/src/clock.rs:27-34`：租约判定（claim/heartbeat/reclaim）全部用 Unix 墙钟毫秒。NTP 向前跳 → 租约提前过期 → 原主仍在校验任务时被接管（`complete` 返回 false，工作成果被静默丢弃，另一 worker 重做）；回拨 → 僵尸租约延长。clock.rs 文档如实写明「租约比较用的是 Unix 毫秒……读本机墙钟」，RESULT.md ④.5 也只把问题推到「跨机部署」，但同一列车的 af-effect-gateway T7 已把同类判定改成单调逻辑毫秒并把它列为坑——同一仓库两套时钟纪律，station 的回拨窗口没有任何持久化高水位兜底。另有一个已声明的 1ms 边界不对称：`heartbeat` 守卫 `lease_until > now` 与 `reclaim` 条件 `lease_until < now` 在 `==` 处既不能续也不能收（B5 ④.3 已钉住，不改判）。
